# A02 — Vérification en deux étapes

## 1. Objectif et contexte

Sécuriser l’accès au back-office par un second facteur. L’écran couvre trois situations : enrôlement d’un premier appareil, vérification d’un code à chaque connexion, et utilisation d’un code de secours.

- Route cible : `/admin/verification-2fa`
- Accès : jeton de challenge uniquement, jamais une session complète.
- Suite : A03, A09b pour un livreur, ou la route demandée initialement.
- 2FA obligatoire pour `ADMIN` et `SUPER_ADMIN` ; recommandée pour les autres rôles internes.

## 2. Rôles autorisés

| Rôle | Enrôlement | Vérification | Code de secours |
| --- | --- | --- | --- |
| `SUPER_ADMIN` | Oui, imposé | Oui | Oui |

| `ORDER_MANAGER` | Oui, proposé | Oui si activé | Oui |

## 4. Composants

| Composant | Usage |
| --- | --- |
| `TwoFactorCodeInput` | Six cellules, collage, navigation clavier |
| `Input` | Code de secours (8 chiffres) |
| `Button` | Vérifier, activer, revenir |
| `Alert` | Erreur, verrouillage, challenge expiré |
| `CopyButton` | Clé manuelle et codes de secours |
| `Checkbox` | « J’ai conservé mes codes de secours » |
| `Spinner` | Vérification en cours |

Le QR code doit être une image générée par le backend ou un composant QR local ; aucune dépendance nouvelle n’est imposée par la spec.

## 5. Les quatre états

| État | Rendu |
| --- | --- |
| Vide / initial | Cellules vides, focus première cellule, bouton désactivé tant que 6 chiffres absents |
| Chargement | Cellules en lecture seule, bouton spinner « Vérification… » |
| Erreur | Code invalide, challenge expiré, compte verrouillé, réseau |
| Succès | Redirection ; enrôlement : affichage des codes de secours avant validation finale |

Détail des erreurs :

- **Code invalide** : « Code incorrect. Vérifiez votre application et réessayez. » Le champ est vidé et refocalisé.
- **5 échecs** : « Trop de tentatives. Réessayez dans 15 minutes. » Compte à rebours affiché.
- **Challenge expiré** : « Votre session de vérification a expiré. Reconnectez-vous. » Bouton vers A01.
- **Enrôlement réussi** : codes de secours affichés **une seule fois**, avec téléchargement `.txt` et copie.
- **Code de secours utilisé** : message « Ce code ne pourra plus être utilisé. » puis redirection.

## 7. Interactions

1. La saisie avance automatiquement à la cellule suivante ; `Retour arrière` recule.
2. Un collage de 6 chiffres remplit toutes les cellules.
3. Le bouton ne s’active qu’avec 6 chiffres ; la soumission automatique est autorisée après le 6e chiffre.
4. « Utiliser un code de secours » bascule vers un champ unique de 8 chiffres.
5. « Retour à la connexion » abandonne le challenge et vide le jeton temporaire.
6. En enrôlement, les codes de secours ne peuvent être fermés qu’après avoir coché la confirmation.
7. Le téléchargement produit `bruny-codes-secours.txt` avec un en-tête et les 8 codes.
8. Aucun bouton « Renvoyer le code » : TOTP ne fonctionne pas par envoi.
9. Le compte à rebours de verrouillage se met à jour chaque seconde et réactive le formulaire à zéro.

## 8. Accessibilité WCAG 2.1 AA

- Groupe de cellules avec `role="group"` et `aria-labelledby`.
- Chaque cellule : `inputmode="numeric"`, `autocomplete="one-time-code"` sur la première, `maxlength="1"`.
- Le collage est annoncé ; les erreurs en `role="alert"`.
- Ne pas déplacer le focus sans action utilisateur en dehors de l’avance automatique.
- Le QR code possède un texte alternatif et la clé manuelle est disponible.
- Les codes de secours sont lisibles en texte, copiables et téléchargeables.
- Contraste ≥ 4,5:1 ; cibles ≥ 44 px ; focus visible.
- Titre de page : « Vérification en deux étapes — Bruny Shopping ».

## 9. Données API

Existant :

- `POST /api/v1/auth/2fa/setup` — génère le secret, le QR et les codes de secours.
- `POST /api/v1/auth/2fa/verify` — vérifie un code TOTP ou un code de secours.

Contrat attendu :

```json
{ "code": "123456", "challengeToken": "…" }
```

Réponse : jetons d’accès et utilisateur. En cas de code de secours, le backend invalide le code utilisé.

| Cas | Statut | Traitement |
| --- | --- | --- |
| Code invalide | 401 | Message générique |
| Challenge expiré | 401 | Retour A01 |
| Trop de tentatives | 429 | Verrouillage 15 min |
| 2FA déjà active | 409 | Proposer la vérification, pas un nouvel enrôlement |

**Absent** : désactivation, régénération des codes, liste des appareils. A16 documente ces dépendances.

## 10. Écarts et dépendances

- Les endpoints de désactivation et de régénération n’existent pas.
- Le login actuel gère l’enrôlement dans la même page ; A02 officialise un écran dédié.
- Aucun mécanisme de « appareil de confiance » : ne pas le promettre.
- Les codes de secours sont à 8 chiffres ; le code TOTP à 6 chiffres.
- Le verrouillage est backend (5 échecs / 15 min) ; l’UI ne fait que l’annoncer.
- La clé manuelle et le QR doivent provenir du backend, jamais être générés côté client.
